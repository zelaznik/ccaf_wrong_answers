SCENARIO: You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.
 
QUESTION: Your team adds a PreToolUse hook to this agent to protect auto-generated code from manual modification. The hook uses the matcher "Write|Edit" and its callback returns a deny decision through hookSpecificOutput whenever tool_input.file_path starts with "generated/". In testing, logging confirms the callback fires for every Write and Edit call, but the prefix check always evaluates false, and the agent continues editing files inside the generated/ directory. What change fixes this hook?
Correct answer
Join the cwd from the hook input with the generated/ directory and compare that absolute path, since file_path is resolved before PreToolUse hooks run.
Explanation
For Write, Edit, and Read, tool_input.file_path is always resolved to an absolute path before PreToolUse hooks execute, so a check for a relative prefix like generated/ never matches. Comparing against an absolute path constructed from the hook input's cwd aligns the check with the actual values the callback receives.
Register the callback under PostToolUse with the same matcher, since that event receives the finalized tool_input after all path resolution completes.
Explanation
PostToolUse fires only after the tool has already executed successfully, so by the time it runs the file in generated/ has already been modified. It can transform what Claude sees or provide feedback, but it cannot prevent the write from happening.
Move the callback to a PermissionRequest hook, since deny decisions through hookSpecificOutput are only enforced at the permission-decision point.
Explanation
PreToolUse hooks fully support deny decisions via hookSpecificOutput, and they run before every tool call regardless of whether permission prompting would occur. PermissionRequest fires only at the permission-decision point, so relying on it would miss tool calls that never trigger a prompt.
Your answer is incorrect
Change the matcher to "Write(generated/**)|Edit(generated/**)" so the hook fires only for Write and Edit calls that target the protected directory.
Explanation
Hook matchers filter by the tool name, not by tool arguments, so argument patterns like Write(generated/**) are not a supported matcher syntax for hooks. Filtering by file path must be done by inspecting tool_input inside the callback itself.
Overall explanation
<p>This scenario tests a documented gotcha in Agent SDK hook design: <b>path normalization happens before your hook runs</b>. For the <code>Write</code>, <code>Edit</code>, and <code>Read</code> tools, <code>tool_input.file_path</code> arrives at a <code>PreToolUse</code> callback already expanded to an absolute path; tildes and relative paths are resolved first. A callback that checks <code>file_path.startswith("generated/")</code> therefore never matches, because the actual value looks like <code>/home/dev/project/generated/client.ts</code>. The reliable pattern is to construct the protected directory's absolute path from the <code>cwd</code> field included in the hook input and compare resolved paths (on Windows, also normalizing separators, since paths arrive with backslashes).</p><p>The mental model to hold is that hooks have two distinct filtering layers. The <b>matcher</b> is coarse-grained and operates on the event's target, meaning the tool name for tool hooks (exact alternatives like <code>Write|Edit</code>, or regex patterns such as <code>mcp__memory__.*</code> for MCP tools). Anything argument-level, like which file or which command, must be inspected inside the callback against <code>tool_input</code>. Argument-pattern matchers like <code>Write(generated/**)</code> are permission-rule syntax, not hook matcher syntax, which is why that fix fails.</p><p>Event choice also matters. <code>PreToolUse</code> runs after Claude has produced tool parameters but before the call is processed, making it the enforcement primitive: its <code>hookSpecificOutput.permissionDecision</code> of <code>deny</code> deterministically blocks the call. <code>PermissionRequest</code> fires only when a permission prompt would occur, so it cannot be relied on for calls that would otherwise auto-approve. <code>PostToolUse</code> fires after the tool succeeded; it is the right place for after-the-fact output normalization or feedback, but the side effect (here, the file edit) has already happened. Choosing an event downstream of the action you want to prevent is a common hook anti-pattern.</p><p>See <a href="https://code.claude.com/docs/en/agent-sdk/hooks">Agent SDK Hooks</a> and <a href="https://docs.anthropic.com/en/docs/claude-code/hooks">Claude Code Hooks Reference</a> for matcher semantics, hook events, and the path normalization behavior.</p>
