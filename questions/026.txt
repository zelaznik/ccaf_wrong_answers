SCENARIO: You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.

QUESTION: Engineers on your team use the agent to remove dead code from legacy services as part of routine cleanup. Last month the agent used Grep to search for references to a handler function, found none, deleted it, and broke a nightly job because the handler was invoked through a method name assembled from strings at runtime. The legacy services also have sparse test coverage. You want the agent to keep removing clearly dead code autonomously while reliably pausing for human input on removals that are genuinely ambiguous. Which design best achieves this?
Correct answer
Add explicit escalation criteria to the agent's instructions (string-based references, reflection, config-driven entry points) with few-shot examples, and have it surface matching candidates to the engineer instead of deleting them.
Explanation
Explicit, operational criteria tell the agent exactly which signals make a removal ambiguous, and few-shot examples demonstrate the boundary between clear-cut and ambiguous cases. This lets the agent proceed autonomously on unambiguous dead code while routing precisely the risky cases to a human, directly matching the stated goal.
Have the agent attach a self-reported confidence score to each proposed removal and automatically delete any candidate that scores above a high threshold.
Explanation
Self-reported confidence is a weak proxy for actual ambiguity: in the incident described, the agent was already confident because its Grep search returned no references, so it would likely have scored that deletion highly. Adding a score does not give the agent new criteria for recognizing dynamic invocation patterns it currently misses.
Instruct the agent to run the test suite after each removal and revert automatically whenever a test fails, treating a passing run as approval to continue.
Explanation
The legacy services are stated to have sparse test coverage, so a passing test run provides little assurance that a dynamically invoked function was safe to delete; the broken nightly job would likely not have been caught. Using tests as the sole arbiter turns weak coverage into a false green light rather than resolving ambiguity.
Your answer is incorrect
Require the engineer to review and approve every individual deletion the agent proposes across each cleanup task.
Explanation
Blanket approval on every deletion eliminates the autonomy the team wants for clear-cut dead code and tends to produce reflexive approvals as engineers tire of confirming obviously safe removals. Escalation is most effective when it is reserved for the cases where human judgment actually adds value.
Overall explanation
<p>The core of this problem is <b>ambiguity resolution design</b>: deciding which situations an agent may resolve autonomously and which it must hand to a human. The failure in the stem is not that the agent lacked diligence; it followed a reasonable procedure (Grep for references, delete if none) that is simply blind to <i>dynamic invocation</i>, where call sites are constructed from strings, reflection, or configuration at runtime. No amount of general caution fixes a blind spot the agent cannot recognize; you have to name the blind spot explicitly.</p><p>That is why the effective pattern is <b>explicit escalation criteria plus few-shot examples</b>. Enumerating concrete ambiguity signals (partial string matches near the function name, reflection utilities, config-driven routing tables, external entry points) converts a vague instruction like "be careful" into checkable conditions, and paired examples of a clearly-dead function versus a dynamically-dispatched one teach the agent where the boundary lies. The agent then keeps its autonomy on the common, unambiguous cases and escalates only where a human's knowledge of the system genuinely changes the outcome.</p><p>The alternatives fail for instructive reasons. Self-reported confidence thresholds assume the agent knows when it is wrong, but in exactly the hard cases the agent's evidence (an empty Grep result) looks conclusive to it, so its confidence is highest where its judgment is worst; this is a design-level weakness of confidence as an escalation trigger, independent of any particular model. Approving every deletion trades one failure mode for another: engineers drown in low-value confirmations and start rubber-stamping, which erodes the very human oversight the policy was meant to provide. Relying on the test suite delegates the ambiguity decision to an oracle the stem tells you is unreliable; with sparse coverage, green tests are silence, not evidence of safety.</p><p>For background on multishot examples as a mechanism for teaching decision boundaries, see <a href="https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/multishot-prompting">Use examples (multishot prompting)</a>, and for agent design patterns see the <a href="https://docs.claude.com/en/api/agent-sdk/overview">Agent SDK overview</a>.</p>
