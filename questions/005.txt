SCENARIO: You are building developer productivity tools using the Claude Agent SDK. The agent helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate code, and automate repetitive tasks. It uses the built-in tools (Read, Write, Bash, Grep, Glob) and integrates with Model Context Protocol (MCP) servers.
 
QUESTION: Your team configures the agent to automate a repetitive task: regenerating API client boilerplate whenever backend contracts change. Team policy requires the project's test suite to pass before the agent finishes any code-modification task. Despite a system prompt instruction stating this requirement, session logs show that in about 10% of runs the agent edits files and then ends its turn without ever running the tests. Which change most reliably enforces the policy?
Correct answer
Add a Stop hook that runs the test suite and blocks turn completion with feedback whenever tests have not passed.
Explanation
The Stop hook fires exactly when the agent attempts to end its turn, making it the correct gate for turn-level completion criteria. By returning a blocking result and feeding the failure back as context, it provides code-level enforcement that sends the agent back into the loop to run or fix the tests, which is far more reliable than hoping the agent remembers the instruction.
Add a PreToolUse hook on the Edit and Write tools that denies file modifications until the test suite has passed.
Explanation
This inverts the required ordering: the policy is that tests must pass after edits are made, not before. Blocking edits until tests pass would deadlock the agent, since it cannot fix failing code without being allowed to edit files, and it does nothing to stop the agent from ending its turn after edits.
Rewrite the system prompt with stronger mandatory language and few-shot examples showing the agent running tests before finishing.
Explanation
Prompt instructions and examples provide only probabilistic compliance, and the observed 10% failure rate occurred despite an existing instruction. When a completion criterion must hold on every run, relying on stronger wording is an anti-pattern compared with deterministic code-level enforcement.
Your answer is incorrect
Add a PostToolUse hook on the Edit and Write tools that runs the test suite after each modification and logs any failures.
Explanation
PostToolUse fires after a tool call has already completed; it can feed information back into context but cannot gate whether the agent ends its turn. Running the full suite after every individual edit is also wasteful, and the agent could still declare the task finished while failures sit in the logs.
Overall explanation
<p>The core architectural distinction here is between <b>probabilistic guidance</b> (system prompts, few-shot examples) and <b>deterministic enforcement</b> (hooks). The failure already occurred with an instruction in place, so the fix must be a mechanism the agent cannot simply ignore. Hooks are code that runs at fixed points in the agent loop, and each hook event guards a different point: <code>PreToolUse</code> gates individual tool calls before they run, <code>PostToolUse</code> fires after a tool has already executed, and <code>Stop</code> fires when the agent wants to end its turn.</p><p>Because the policy is a <i>turn-level completion criterion</i> ("do not finish until tests pass") rather than a per-tool ordering rule, the <b>Stop hook</b> is the right enforcement point. It can run the test suite at exactly the moment the agent tries to finish and return a blocking result whose message is fed back to the agent as context, effectively telling it "you are not done" and sending it back into the loop to run or fix the tests. In practice the hook should check state and return specific, actionable feedback (for example, which tests failed and why) so the agent can make progress rather than repeatedly hitting the same block. This makes it the most reliable lifecycle enforcement point for completion criteria, and it pairs naturally with permissive execution modes: the loop can proceed hands-off during edits while the Stop gate verifies correctness at the end.</p><p>The distractors each pick the wrong control point. A <code>PreToolUse</code> deny on edits creates a deadlock because code cannot be fixed without editing. A <code>PostToolUse</code> hook can observe and inject feedback but cannot prevent the turn from ending, so a determined-to-finish agent still ends with failing tests. Stronger prompting merely raises the compliance probability without guaranteeing it. See <a href="https://code.claude.com/docs/en/agent-sdk/hooks">Agent SDK Hooks</a> and <a href="https://code.claude.com/docs/en/agent-sdk/permissions">Configure permissions</a> for how hooks intercept the agent loop and where they sit in the permission evaluation order.</p>
