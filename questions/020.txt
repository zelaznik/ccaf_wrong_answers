SCENARIO: You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.

QUESTION: An engineer on your team proposes an optimization: since the document analysis subagent's findings are consumed by the synthesis subagent, the analysis subagent should hand its results directly to the synthesis subagent instead of routing them through the coordinator, which the engineer argues adds unnecessary overhead. All subagents are defined programmatically via the SDK's agents parameter and are invoked by the coordinator through the Agent tool. How should you respond to this proposal?
Migrate the pipeline to agent teams so the analysis and synthesis agents can message each other directly without a coordinator relaying results.
Explanation
Agent teams do support direct inter-agent messaging, but they are an experimental feature that runs multiple Claude Code instances with substantially higher token cost. Restructuring a working coordinator-subagent pipeline around them to avoid one relay step is a poor tradeoff for this sequential research flow.
Correct answer
Keep the coordinator as the hub: it receives the analysis result and passes the relevant findings in the synthesis subagent's delegation prompt.
Explanation
This matches how SDK subagents actually work: each subagent's final message returns to the agent that spawned it, and the only context a new subagent receives is the prompt passed at invocation. The coordinator is also the natural place to aggregate analysis findings with web search results before synthesis, so hub routing is both the supported mechanism and the correct architecture.
Instruct the synthesis subagent in its prompt to reference the analysis subagent's earlier findings, since both subagents run within the same session.
Explanation
This relies on a misconception that subagents share a session context. Each subagent defined via the agents parameter starts with a fresh, isolated context window; the only information it receives is the delegation prompt string, so it cannot see a sibling subagent's findings no matter what its prompt instructs.
Your answer is incorrect
Have the analysis subagent spawn the synthesis subagent as a nested subagent, passing its complete findings in the nested delegation prompt.
Explanation
Nested spawning is technically possible, but the synthesis output would then return to the analysis subagent rather than the coordinator, fragmenting orchestration. The synthesis agent also needs findings from the web search subagent, which the analysis subagent does not have, so this restructuring breaks the aggregation the coordinator performs.
Overall explanation
<p>The coordinator-subagent pattern in the Claude Agent SDK is a <b>hub-and-spoke</b> architecture by design. Each subagent is a separate agent instance with an isolated context window: it starts fresh, receives only the delegation prompt the invoking agent writes, does its work, and returns its final message to whoever spawned it. There is no channel for one sibling subagent to hand context to another; the parent is the only integration point. This is not an accidental limitation, it is the mechanism that gives the pattern its value: intermediate tool calls and verbose exploration stay inside each subagent, and the coordinator sees only distilled results it can route, filter, and combine.</p><p>In this pipeline the coordinator's relay role is doing real work. The synthesis subagent needs findings from <i>both</i> the web search subagent and the document analysis subagent, and only the coordinator holds both results. Passing them explicitly in the synthesis subagent's delegation prompt is how context transfer works; treating that step as removable overhead misunderstands the model.</p><p>The alternatives fail for concrete reasons. Prompting the synthesis subagent to reference the analysis subagent's earlier work cannot succeed because subagents do not share a session context; a non-fork subagent always starts fresh, and a prompt instruction cannot conjure information that was never placed in its context. <b>Agent teams</b> do offer direct inter-agent messaging, but they are experimental, run as multiple instances, and cost significantly more tokens, which is a heavy price to avoid one prompt relay in a sequential pipeline. Nested spawning routes the synthesis result back to the analysis subagent instead of the coordinator, breaking both aggregation and error handling, which should flow upward through the hub.</p><p>See <a href="https://code.claude.com/docs/en/agent-sdk/subagents">Subagents in the SDK</a> for context isolation and delegation mechanics, and <a href="https://code.claude.com/docs/en/agent-teams">Agent teams</a> for how direct inter-agent messaging differs from single-session subagents.</p>
