SCENARIO: You are using Claude Code to accelerate software development. Your team uses it for code generation, refactoring, debugging, and documentation. You need to integrate it into your development workflow using custom slash commands and CLAUDE.md configuration, and to know when to use plan mode rather than direct execution.

QUESTION: Your team's /scaffold command, defined in a legacy .claude/commands/scaffold.md file, generates boilerplate for new services. Over time the file has grown to contain several lengthy code templates pasted inline plus a shell helper script that Claude is told to retype and run, and when the command is invoked all of this content is loaded into the conversation. You want the core instructions to stay small, the templates to be read only when a particular one is needed, and the helper script to be runnable without its contents being loaded as context. How should you restructure this?
Correct answer
Migrate it to a project skill at .claude/skills/scaffold/SKILL.md, move each template into a supporting file it references, and keep the helper script in the folder as an executable.
Explanation
Skills are folders, so they can carry supporting files alongside a lean SKILL.md entry point. Referenced files are read only when Claude needs that specific depth, and scripts in the folder can be executed rather than loaded as context, which is exactly what commands as single markdown files cannot provide.
Move the templates and helper script into the project-level CLAUDE.md so they are available in every conversation, and slim the command file down to just the invocation steps.
Explanation
CLAUDE.md is loaded into every session, so this converts occasionally needed template content into permanent context overhead for all work, including sessions that never scaffold anything. It solves the command file's size at the cost of bloating every conversation, the opposite of on-demand loading.
Split the workflow into several smaller slash commands in .claude/commands/, one per template, and have developers invoke them in sequence when scaffolding a new service.
Explanation
Splitting into multiple commands fragments a single workflow and pushes orchestration onto developers, who must remember the correct sequence. Each command file still loads its full contents when invoked, and this does nothing to make the helper script executable rather than retyped from context.
Your answer is incorrect
Keep the single .claude/commands/scaffold.md file and use @import statements to pull the templates and helper script in from separate modular markdown files stored in the repository.
Explanation
The @import syntax is a CLAUDE.md mechanism for modularizing memory files, not a documented feature of command files. Even conceptually, importing the content would still bring it all into context on load rather than making templates available on demand or the script executable without loading.
Overall explanation
<p>Claude Code has merged custom commands into <b>skills</b>: a file at <code>.claude/commands/scaffold.md</code> and a folder at <code>.claude/skills/scaffold/SKILL.md</code> both create the same <code>/scaffold</code> command, and legacy command files keep working. The reason the docs recommend skills is structural. A command is a single markdown file, so everything it needs must live inline and is loaded wholesale when the command's content is brought into context. A skill is a <i>directory</i>: <code>SKILL.md</code> is a lean entry point, detailed material sits in supporting reference files that Claude reads only when it actually needs that depth, and scripts stored in the folder can be <i>executed</i> rather than pasted into context. This progressive-disclosure design is the tradeoff skills exist to make: only skill descriptions are held in context during a normal session, and the full <code>SKILL.md</code> plus any referenced files load on demand, keeping the context window free for the work itself.</p><p>The distractors each misapply a real mechanism. <code>@import</code> modularizes CLAUDE.md memory files, not command definitions, and modularity alone would not make loading conditional. Moving templates into the project CLAUDE.md is the classic anti-pattern of placing occasional, task-specific material into always-loaded configuration; the rule of thumb is that universal conventions belong in CLAUDE.md while task-specific procedures belong in skills. Splitting one workflow across several commands trades a maintenance problem for an orchestration problem without changing how much content each command brings in when its material is loaded.</p><p>See <a href="https://docs.anthropic.com/en/docs/claude-code/slash-commands">Slash commands</a> for how commands and skills relate, skill folder structure, and frontmatter options.</p>
