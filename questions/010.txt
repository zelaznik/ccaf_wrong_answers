SCENARIO: You are building a multi-agent research system using the Claude Agent SDK. A coordinator agent delegates to specialized subagents: one searches the web, one analyzes documents, one synthesizes findings, and one generates reports. The system researches topics and produces comprehensive, cited reports.
 
QUESTION: Analysts submit research requests to the system, and a review of unsatisfactory reports shows a consistent pattern: when a request is genuinely ambiguous (for example, "research the merger's impact" when the topic area includes several recent mergers), the coordinator silently picks one interpretation and runs the full subagent pipeline, producing a well-cited report on the wrong question. You want the coordinator to pause and ask the requesting analyst for clarification on genuinely ambiguous requests while still proceeding autonomously on clear ones. Which design most effectively achieves this?
Have the coordinator enumerate every plausible interpretation of ambiguous requests, run the full subagent pipeline for each in parallel, and deliver all resulting reports to the analyst.
Explanation
Running the complete pipeline for every plausible interpretation multiplies token cost and latency and shifts the disambiguation burden onto the analyst after the expensive work is done. A short clarifying exchange before decomposition resolves the ambiguity at a fraction of the cost.
Your answer is incorrect
Require the coordinator to begin every research request with a round of clarifying questions to the analyst before decomposing the topic into subagent tasks.
Explanation
Forcing clarification on every request adds friction to the majority of requests that are already clear and trains analysts to ignore the questions. The goal is selective escalation on genuinely ambiguous requests, not unconditional escalation.
Correct answer
Define explicit criteria in the coordinator's prompt for what makes a request ambiguous, with few-shot examples contrasting requests it should clarify with the analyst versus requests it should decompose and run.
Explanation
Explicit escalation criteria paired with contrasting few-shot examples give the coordinator a concrete, demonstrated decision boundary between ambiguous and clear requests. This is the reliable pattern for ambiguity resolution because it grounds the escalation decision in observable request characteristics rather than the model's self-assessment.
Have the coordinator output a self-reported confidence score for its chosen interpretation of each request and route the request back to the analyst whenever the score falls below a tuned threshold.
Explanation
Self-reported confidence is an unreliable proxy for actual ambiguity because the model is often most confident precisely when it has silently committed to a single plausible interpretation. Thresholding on such scores does not reliably separate ambiguous requests from clear ones.
Overall explanation
<p>The failure here is a classic <b>ambiguity resolution</b> problem: the coordinator commits to one plausible interpretation instead of recognizing that the request itself is underspecified. The reliable fix is to make the escalation decision explicit rather than implicit. By writing concrete criteria for ambiguity into the coordinator's instructions (multiple named entities could match, the analysis dimension is unstated, the time window is unclear) and pairing them with <b>few-shot examples</b> that contrast requests warranting clarification with requests that should proceed, you give the model an observable decision boundary it can pattern-match against. Contrasting examples are consistently more effective than prose rules alone at communicating this kind of judgment, as described in <a href="https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/multishot-prompting">Use examples (multishot prompting)</a>.</p><p>The mental model to internalize is that <i>self-reported confidence is not a measurement of ambiguity</i>. A model that has silently latched onto one interpretation typically reports high confidence in it; the cases you most need to catch are exactly the ones where the score misleads. Explicit criteria anchor the decision in features of the request, not in the model's assessment of its own reasoning.</p><p>The other designs fail on cost or friction grounds. Fanning out the full research pipeline across every plausible interpretation multiplies token spend and latency across four subagent stages and still forces the analyst to disambiguate afterward, when a single upfront question would have resolved it. Mandatory clarification on every request is over-escalation: it penalizes the clear majority of requests and erodes analyst trust in the questions that actually matter. Effective agent design keeps the agent autonomous where it can make meaningful progress and surfaces a human checkpoint precisely where it cannot, a principle discussed in <a href="https://www.anthropic.com/engineering/building-effective-agents">Building effective agents</a> and supported by coordinator patterns in the <a href="https://docs.claude.com/en/api/agent-sdk/overview">Agent SDK overview</a>.</p>
