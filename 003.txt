SCENARIO: You are building a customer support resolution agent using the Claude Agent SDK. The agent handles high-ambiguity requests like returns, billing disputes, and account issues. It has access to your backend systems through custom Model Context Protocol (MCP) tools (get_customer, lookup_order, process_refund, escalate_to_human). Your target is a first-contact resolution rate of 80% or higher, with reliable escalation to a human when a case falls outside what the agent should handle.
 
QUESTION: Your team is using Claude Code to implement the escalation decision logic that determines when this agent should call escalate_to_human instead of process_refund. Over three iterations, you described the escalation policy in prose, Claude implemented it faithfully, and only while reviewing the resulting behavior did you discover scenarios you had never considered (chargebacks already in dispute, refund requests exceeding a customer's lifetime spend, repeat contacts within 24 hours). You conclude the gaps are in your own understanding of the escalation domain, not in Claude's compliance with your instructions. Which refinement approach would most effectively break this cycle?
Write a test suite covering the escalation policy first, then share failing test output so Claude iterates until every test passes.
Explanation
Test-driven iteration gives Claude a verifiable check to iterate against, which is powerful when the acceptance criteria are known. Here the tests can only encode scenarios the developer has already thought of, so the unanticipated cases like chargebacks in dispute or repeat contacts would have no tests and Claude could pass the entire suite while still missing them.
Switch to plan mode so Claude presents its full implementation approach for your review and approval before making any file edits.
Explanation
Plan mode separates research from edits and lets you review Claude's proposed approach, but a plan can only cover scenarios that someone has raised. If neither you nor the prompt mentions chargebacks in dispute or repeat contacts, you would likely approve a plan that omits them, so the same discovery-after-the-fact cycle continues.
Your answer is incorrect
Provide two or three concrete input and output examples of escalation decisions in the prompt so the expected behavior is communicated unambiguously.
Explanation
Concrete examples are the right technique when you know the desired behavior but prose descriptions are being interpreted inconsistently. Here the stated problem is that the developer does not yet know all the scenarios, so any examples they write will only cover cases they have already anticipated and the unknown edge cases will remain unaddressed.
Correct answer
Have Claude interview you with questions about escalation edge cases and policy boundaries, then implement based on your answers.
Explanation
The interview pattern is designed for exactly this situation: an unfamiliar domain where the developer cannot enumerate requirements up front. Having Claude probe for edge cases and failure modes surfaces design considerations before implementation, so gaps in the developer's understanding are exposed during requirements gathering rather than discovered after reviewing finished code.
Overall explanation
<p>Iterative refinement techniques are not interchangeable; each one targets a different source of error, and choosing well starts with diagnosing where the gap actually lives. When Claude misinterprets a rule you understand perfectly, <b>concrete input/output examples</b> communicate the transformation unambiguously. When outputs fail against known criteria, <b>verifiable checks</b> such as tests let Claude iterate until they pass. But when the failure pattern is that you only recognize requirements after seeing the output, the missing knowledge is on your side of the collaboration, and no amount of clearer instruction or tighter verification can encode requirements you have not yet discovered.</p><p>The <b>interview pattern</b> inverts the usual flow: instead of you specifying and Claude implementing, Claude asks questions first. A model that has seen many escalation and refund systems will probe for boundary conditions (disputed charges, spend thresholds, repeat-contact windows) that a developer new to the domain would not think to specify. This moves discovery from post-implementation review, where each missed case costs a full iteration, to a cheap up-front conversation. It pairs naturally with plan mode afterward: interview to establish requirements, plan to structure the implementation, then execute.</p><p>The distractors each solve an adjacent problem. Examples pin down behavior for <i>known</i> cases; plan mode gives you a checkpoint to review an approach, but you can only veto omissions you notice; and test-driven iteration keeps Claude honest against criteria you wrote, yet a test suite built from an incomplete mental model of the domain simply certifies confidently incomplete logic. See <a href="https://code.claude.com/docs/en/best-practices">Claude Code Best Practices</a> and <a href="https://code.claude.com/docs/en/common-workflows">Common Workflows</a> for guidance on matching refinement techniques to failure modes.</p>
